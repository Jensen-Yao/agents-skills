# 补天/SRC 平台提交知识(以项目页当前规则为准,以下为常见口径)

## 专属 SRC 与公益 SRC 的区分

| 项 | 专属 SRC | 公益 SRC |
|---|---|---|
| 发起方 | 厂商/企业自己的漏洞收集项目(私有项目) | 面向公众的公益项目/众测 |
| 资产边界 | 项目页列明的厂商资产 | 项目页列明的公益目标 |
| 定级奖励 | 按厂商项目规则 | 按公益规则 |
| 典型入口 | pep.butian.net 项目页(需登录) | 公益 SRC 项目页 |

要点:

1. 报告"提交平台"栏必须与项目实际类型一致:**先确认类型,再写报告**;用户说改公益/专属就按用户说的填。
2. 项目页需登录才能查看详情时,向用户索要:厂商名称、资产范围、允许测试类型、禁止事项、提交要求、评级标准。
3. 项目页"厂商资产范围:无限制"等模糊表述:与用户确认解读(如是否含关联域名),写入 `00-scope/scope.md` 后再测,不自行扩大。

## 漏洞类别与评级

- 漏洞类别:Web 漏洞、IoT 漏洞、工控漏洞、操作系统及通用软件漏洞
- 漏洞类型:事件型 / 通用型
- 危害程度(常见定级):
  - **低危 1kb(无积分)**:druid 未授权、短信/邮箱轰炸、源码泄露、信息泄露、被挂黑页等
  - **中危 2-3kb**:SQL 注入、越权、XSS、弱口令等(事件型 SQL 注入属中危;SQL 注入提权至 shell 算高危)
  - **高危 4kb**:命令执行、代码执行、文件上传、其余可 getshell 的漏洞等
- 平台"漏洞类型"分类字段可选值:XSS、配置错误、弱口令、入侵事件、疑似被黑、文件上传、信息泄露、存在后门、逻辑漏洞、代码执行、命令执行、SQL 注入、解析漏洞

报告定级规则:

1. "漏洞类型(平台分类)"从上述分类字段选最贴合的一个(如:开放重定向→逻辑漏洞;验证码死代码→逻辑漏洞;明文传输/HSTS 缺失→配置错误)。
2. 定级诚实:明确区分"已实测"与"推断"(如 SSO Token 泄露仅推断时注明);平台明示低危无积分时告知用户。
3. 常见类型映射参考:开放重定向≈逻辑漏洞(若审核认定低危属预期);信息泄露/配置缺陷→低危 1kb;弱口令/认证缺陷→中危 2-3kb。

## 漏洞详情填写要求

1. **基础信息**:漏洞利用的完整过程,相关 URL、截图、代码以及 POC。若不符合规则,漏洞可能审核不通过。
2. **IoT 漏洞**还需提供:
   - 漏洞触发对应的二进制位置
   - 目标配置情况
   - 漏洞研究环境:真实硬件设备需提供购买链接;模拟仿真需描述环境搭建与调试方法等
3. 利用过程中使用到组件:提供下载链接,或压缩后在附件处上传。
4. 较复杂漏洞:可提供攻击过程视频/图片;图片可在细节中直接上传;视频提供链接或压缩后在附件处上传。
5. PoC/Exp 语言不限,要求思路清晰、可读性高、易于复现。
6. 提供的信息越全面,奖励越高。

## 提交附件规范与证据打包流程

附件限制:

- 附件仅支持上传**压缩后的组件/固件/视频**,只能上传 **zip/rar**,且不超过 **50M**。
- 截图/图片:在"漏洞细节"中**直接上传**,不放进压缩包。
- 视频:提供链接或压缩后附件上传。

打包流程(阶段 4 收尾执行,产出到 `submit/`):

1. 每个漏洞一个压缩包,命名 `BUG-<编号>-<英文简述>.zip`。
2. 包内文件一律 **ASCII 文件名**(避免中文乱码),建议结构:
   - `01_xxx.png`、`02_xxx.png` — 截图(同时保留在 `03-verify/evidence/` 供细节内直传)
   - `03_xxx.txt` — curl 原始请求/响应(响应头等)
   - `poc_xxx.py` — POC 脚本(纯标准库、可直接运行、含注释)
   - `report_xx_xxx.md` — 报告原文(方便复制到详情栏)
3. Windows 打包(Compress-Archive)注意:先建 staging 目录、拷入重命名后的文件,再压缩;压缩后用 `[IO.Compression.ZipFile]::OpenRead` 列出包内条目校验文件齐全。
4. 交付时给用户列出"每个报告需提交的附件清单"(截图文件 + 压缩包)。
5. 低危 1kb 档(平台无积分)提示用户自行决定是否提交。
